## 四、conftest.py 4 个 Fixture 详解

### 记忆口诀：「数据库会话地址清理，4 个 fixture 各管一摊」

```
┌──────────────────────────────────────────────────────────────────┐
│ fixture 时间线：  前置（yield 前）  →  测试体  →  后置（yield 后）  │
└──────────────────────────────────────────────────────────────────┘
```

### 4.1 `db` — 数据库校验器

```
scope = "session"   ← 整个测试过程只创建 1 次
┌─────────────────────────────────────────────────┐
│ 前置：checker = DatabaseChecker()                │
│ yield → checker 交给测试用例                      │
│ 后置：无（DatabaseChecker 无状态，不需要清理）      │
└─────────────────────────────────────────────────┘
```

### 4.2 `api_session` — HTTP 会话

```
scope = "function"  ← 每个用例独立 Session
┌─────────────────────────────────────────────────┐
│ 前置：session = requests.Session()               │
│       session.headers.update(Content-Type: JSON) │
│ yield → session 交给测试用例                      │
│ 后置：session.close()（关闭 TCP 连接）             │
└─────────────────────────────────────────────────┘
```

**为什么用 Session 而不是直接 requests.get()**：
- Session 复用底层 TCP 连接（多次请求只需一次三次握手）
- 统一设置 headers（不用每个请求都写 Content-Type）

### 4.3 `base_url` — 被测地址

```
scope = "function"  ← 轻量，每次调一下而已
┌─────────────────────────────────────────────────┐
│ return "http://127.0.0.1:5000"                  │
│ 用 fixture 的好处：以后可以命令行 --base-url 覆盖  │
└─────────────────────────────────────────────────┘
```

### 4.4 `created_ids` — 自动清理列表（最重要！）

```
scope = "function"  ← 每个用例独立清理列表
┌─────────────────────────────────────────────────┐
│ 前置：ids = []                                   │
│ yield → ids 交给测试用例（用例往里 append ID）     │
│ 后置：for id in ids: delete_user_by_id(id)       │
│       except Exception: pass（删不掉也不影响测试） │
└─────────────────────────────────────────────────┘
```

**这是解决"测试污染"的核心机制**：
- 测试创建数据 → 登记 ID → 测试结束自动删
- 保证数据库在测试前后一模一样
- 即使测试中途失败，只要登记了 ID 就能清理

## 七、核心知识点速查

### 7.1 pytest 相关

| 概念 | 一句话解释 | 在哪用 |
|------|-----------|--------|
| `conftest.py` | pytest 自动发现并加载的特殊文件 | tests/api/conftest.py |
| `@pytest.fixture` | 装饰器，把函数变成"夹具" | conftest.py 里 4 个函数 |
| `scope="session"` | 整个测试过程只创建一次 | db fixture |
| `scope="function"` | 每个测试函数创建新实例 | api_session, created_ids |
| `yield` | 暂停，把值交给测试，跑完再回来清理 | db(ctx 不清理), api_session(ctx close), created_ids(ctx 清理) |
| `@pytest.mark.parametrize` | 数据驱动，一份代码跑多组数据 | TestUserCreate |
| `-v` | verbose，显示详细信息 | 命令行 |
| `-s` | 不捕获 print 输出（调试用） | 命令行 |
| `--html=xxx.html` | 生成 HTML 报告 | 命令行 |
| `--self-contained-html` | CSS 内嵌进 HTML | 命令行 |

### 7.2 requests 相关

| 方法 | 对应 HTTP | 用法 |
|------|----------|------|
| `session.get(url)` | GET | 查询 |
| `session.post(url, json={...})` | POST | 新增 |
| `session.put(url, json={...})` | PUT | 修改 |
| `session.delete(url)` | DELETE | 删除 |
| `resp.status_code` | — | 拿 HTTP 状态码（200, 201, 400, 404, 500） |
| `resp.json()` | — | 把响应体的 JSON 转成 Python 字典 |

### 7.3 两层状态码

```
HTTP 状态码（resp.status_code）       业务状态码（result["code"]）
─────────────────────────────        ─────────────────────────
协议层面的成功/失败                    业务层面的含义
200 = 请求成功                        200 = 查询/修改/删除成功
400 = 客户端错误                      201 = 创建成功
404 = 未找到                          400 = 客户端参数错误
500 = 服务器错误                      404 = 资源不存在
                                     500 = 服务器内部错误
```

**本项目接口统一返回 HTTP 200，通过 JSON body 里的 code 区分业务状态。**

## 九、数据库落地校验（什么是"第三只眼"）

### 为什么不能只看接口返回

```
只看接口返回 = 接口说"创建成功"你就信了
            万一接口有 bug，返回了 201 但数据没写进去呢？

数据库落地校验 = 接口说创建成功 → 我自己去数据库查
               SELECT * FROM users WHERE id = 新ID
               数据真的在 → 才算通过
               数据不在 → 测试失败
```

### 代码体现

```python
# 你的测试里有两层断言：
assert result["code"] == 201                    # ① 信了接口
user = db.get_user_by_id(new_id)                 # ② 自己去数据库验证
assert user is not None                          #    数据真的在！
assert user["name"] == "正常创建"
```

**面试说法**：「接口测试我也做数据库落地校验——绕过被测应用，直接通过 PyMySQL 连 MySQL 执行 SELECT，确认数据真实落库。这叫"不以接口返回为准，以数据库状态为准"。」

## 十、测试数据清理机制详解

```
问题：测试创建了用户 → 数据留在了数据库 → 下次跑测试邮箱冲突 → 测试失败
     ↓
解决：created_ids fixture
     ↓
机制：
  ┌──────────────────────────────────────┐
  │ ids = []                             │ ← 前置：空列表
  │ yield ids                            │ ← 交给测试
  │                                      │
  │ 【测试体中】                           │
  │ new_id = result["data"]["id"]        │
  │ created_ids.append(new_id) ← 登记！  │
  │                                      │
  │ 【yield 之后】                         │
  │ for user_id in ids:                  │
  │     delete_user_by_id(user_id)       │ ← 清理！
  └──────────────────────────────────────┘
```

**关键设计点**：
1. `append` 写在 `assert` 前面 → 即使断言失败，数据也已登记，会被清理
2. `try/except/pass` → 清理失败不影响测试结果（测试本身已经通过了）
3. `created_ids.remove(user_id)` → 有些用例自己删了数据（如 test_delete_user_success），就从列表里移除，避免重复删除

## 十一、遇到的坑 & 排查过程

```
问题 1：ConnectionRefusedError（Flask 没启动）
  现象：pytest 报 目标计算机积极拒绝
  排查：Flask 是需要手动启动的独立进程
  解决：开两个终端，终端1跑 Flask，终端2跑 pytest
  教训：接口测试 = 客户端发请求 + 服务端处理，服务端不跑=没结果

问题 2：assert 201 == 200（HTTP 状态码 vs 业务状态码）
  现象：期望 resp.status_code == 201，实际是 200
  原因：Flask 的 jsonify() 默认返回 HTTP 200，业务状态在 JSON body 里
  解决：分开断言 → HTTP 200 + result["code"] == 201
  收获：理解了两层状态码的区别

问题 3：(1062, "Duplicate entry") 邮箱重复
  现象：创建测试返回 500，数据库报邮箱重复
  原因：上次测试失败，数据残留
  解决：手动清数据库 → DELETE FROM users WHERE email LIKE '%@test.com'
  收获：理解了测试污染问题 → created_ids 机制的价值

问题 4：JSONDecodeError（空请求体导致）
  现象：不传 json 参数 → resp.json() 报错
  原因：不传 json → 请求体为空 → Flask 框架层返回 HTML 错误页
  解决：传 json={}（空字典）而不是不传 json
  收获：json={} = 传空 JSON 对象，不传 json = 请求体为空

问题 5：IndentationError（缩进错误）
  现象：class TestUserCreate: 前面多了 2 个空格
  解决：类的缩进必须是 0（顶格），方法 4 空格，方法体 8 空格
  收获：Python 对缩进要求非常严格，混用空格和 Tab 是大忌
```

## 十二、面试必问答

### Q1：conftest.py 里放了什么？为什么这样设计？

> 我定义了 4 个 fixture：db（数据库校验器，session 级别复用）、api_session（HTTP Session，function 级别独立）、base_url（被测地址）、created_ids（测试数据自动清理）。这样用例只写测试逻辑，准备和清理交给 fixture 统一管理。

### Q2：fixture 的 scope 有哪些？你分别用在什么场景？

> session 级别给无状态的工具类（DatabaseChecker），只创建一次；function 级别给有状态的对象（HTTP Session、清理列表），每个用例独立，互不污染。

### Q3：yield 和 return 的区别？

> return 直接结束函数；yield 暂停并把值交给测试用例，等测试跑完之后从 yield 的下一行继续执行——这就是 fixture 能做"后置清理"的原理。

### Q4：你是怎么做数据落地校验的？

> 创建/修改接口调用后，不用接口返回的 data 做最终判断，而是用 DatabaseChecker 直连 MySQL 执行 SELECT，确认数据真实写入。这叫"不以接口返回为准，以数据库状态为准"。

### Q5：怎么保证测试不污染数据库？

> 用了 created_ids 这个 fixture —— 测试创建数据后立刻把 ID 加到列表里，yield 之后自动从数据库删除。即使测试中途断言失败，只要登记了就能清理。

### Q6：parametrize 在你项目里怎么用的？

> 我把"创建用户缺必填字段"的多个场景做成了数据驱动，把输入数据和断言关键词抽成参数，一份代码覆盖多组数据。新增场景只加参数行，不改代码逻辑。

### Q7：测试报告怎么生成的？

> 用 pytest-html 插件，跑测试时加 `--html=reports/api_report.html --self-contained-html`，CSS 内嵌，单文件就能在浏览器里看。报告包含环境信息、通过率、每条用例的执行结果。

### Q8：500 错误怎么排查？

> 先看接口返回的 message 有没有错误描述。如果没有，就看 Flask 控制台输出的堆栈——traceback 会定位到具体代码行。线上环境就用 `tail -f` 实时看应用日志。
