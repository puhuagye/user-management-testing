### Q2：自动化框架是怎么设计的？

**答：** 分三层架构：

- **夹具层（conftest.py）**：统一管理测试前置和后置，比如数据库连接、HTTP 会话、测试数据清理。用 pytest fixture 的 scope 控制复用粒度——无状态工具类用 session 级别只创建一次，有状态对象用 function 级别每个用例独立。
- **工具层（common/）**：封装数据库操作（DatabaseChecker）和配置管理。测试用例不直接连数据库，而是通过工具层的类来操作。
- **用例层（test_*.py）**：只写测试逻辑——发请求、拿响应、assert 断言。不关心数据库怎么连、浏览器怎么启动。

这样分层的好处：换一个接口实现，只需要改工具层；换前端框架，只需要改 Page Object 层；测试用例本身不受影响。

### Q3：接口测试是怎么设计用例的？

**答：** 我从四个维度来设计：

1. **HTTP 状态码**：检查协议层面的成功和失败
2. **业务状态码**：检查 JSON 返回体里的业务 code（我们的接口 HTTP 200 返回，但业务 code 区分成功 201 和失败 400）
3. **数据库落地校验**：操作后直连 MySQL 查一下，确认数据实际写入或删除
4. **边界和异常**：缺必填字段、空请求体、重复删除（幂等性）、请求不存在的资源

每一个接口按这四个维度来写，最终 13 条用例覆盖了全部 5 个接口。

---

### Q4：数据库落地校验是什么？怎么做的？

**答：** 就是"不以接口返回为准，以数据库实际状态为准"。比如接口返回了"创建成功"，但我不直接信它——我用 PyMySQL 直连数据库，执行 `SELECT * FROM users WHERE id = 新ID`，确认这条数据真的在数据库里。

我专门写了一个 DatabaseChecker 类，封装了 get_user_by_id、delete_user_by_id 这些方法，测试用例调用它来直接操作数据库。

这样做的好处：万一接口有 bug——返回了成功但数据没写进去——我能在测试阶段就发现。

**追问：那你绕过接口查数据库，是不是测了两遍？**
不是重复。接口测试验证的是"接口有没有 bug"，数据库校验是给接口测试当裁判——验证接口返回的结果是不是真的。

### Q5：Page Object 模式是什么？你项目里怎么用的？

**答：** Page Object 是把每个网页封装成一个类：

- 类属性 = 页面元素的定位方式（放在一起，集中管理）
- 方法 = 页面可执行的操作（填表单、点按钮）和可查询的状态（获取文字、判断是否显示）

测试用例里只调 page 的方法，不直接写 `find_element`。举个例子：如果前端把"提交按钮"的 id 从 `btn-submit` 改成了 `btn-create`，没有 Page Object 的话，所有用例里的 `find_element` 都要改。有了 Page Object，只改这一个类的元素定位就行，用例完全不受影响。

我的项目里写了三个 Page 类：
- **UserListPage** — 用户列表页（查看、点击编辑/删除按钮）
- **CreateUserPage** — 新增用户页（填表单、提交、获取错误提示）
- **EditUserPage** — 编辑用户页（获取预填数据、修改提交）

### Q6：fixture 的作用是什么？yield 和 return 的区别？

**答：** fixture 是 pytest 提供的"夹具"机制，用来管理测试的前置准备和后置清理。

`yield` 和 `return` 的关键区别：
- `return` 直接结束函数，把值返回
- `yield` 暂停函数，把值交给测试用例，等测试跑完之后**从 yield 的下一行继续执行**——这就是 fixture 能做后置清理的原理

我的项目里用了 4 个 fixture：
- `db`（session 级别）——提供数据库校验器，整个测试只创建一次
- `api_session`（function 级别）——每个用例独立的 HTTP 会话
- `base_url`——提供被测地址
- `created_ids`（function 级别）——测试数据自动清理。用例创建数据后把 ID 加到列表，yield 之后自动从数据库删除

### Q7：UI 测试遇到元素定位不到怎么排查？

**答：** 四步排查法：

1. **等一等**：用 WebDriverWait + expected_conditions 显式等待，而不是 time.sleep 盲等。因为 AJAX 加载、页面跳转、alert 弹窗都需要时间
2. **换定位方式**：id 不行换 name，name 不行换 CSS_SELECTOR，CSS 不行换 XPath
3. **检查 iframe**：如果元素在 iframe 里面，需要先 `driver.switch_to.frame()` 切进去
4. **检查是否被遮挡**：弹窗、下拉菜单可能挡住元素

我项目里遇到过一个坑：HTML5 的 `required` 属性会拦截前端 JS 校验，导致校验逻辑走不到，后来用 `novalidate` 属性绕过了。

---

### Q8：测试数据怎么保证不污染数据库？

**答：** 我用了一个 `created_ids` fixture 做自动清理：

- 测试创建数据后，立刻把 ID append 到一个列表
- fixture 的 yield 之后遍历这个列表，逐个从数据库删除
- 关键设计：append 写在 assert 前面，即使断言失败，数据也已登记，会被清理
- 清理用 try/except/pass，清理失败不影响测试结果

### Q9：pytest-html 报告怎么生成的？报告里有什么？

**答：** 一条命令：
```bash
pytest tests/ -v --html=reports/full_report.html --self-contained-html
```

`--self-contained-html` 让 CSS 样式内嵌到 HTML 里，单个文件就能在浏览器打开。

报告里包含：环境信息（Python 版本、平台）、通过率统计、每条用例的执行结果（通过/失败/跳过）、失败用例的错误信息和调用栈。

### Q10：项目中遇到的最大的困难是什么？怎么解决的？

**答（挑一个你最有感的）：**

**困难1：MySQL 连接失败**
排查了三个问题：服务名是 MySQL80 不是 MySQL；端口号是安装时选的 3307 不是默认 3306；MySQL 8.0 需要 cryptography 包做认证。三个问题逐个解决后才连上。

**困难2：alert 弹窗处理**
UI 测试里点"删除"会弹出 confirm 确认框，但 alert 不是瞬间出现的。一开始用 time.sleep 盲等，不稳定。后来查文档发现可以用 WebDriverWait + EC.alert_is_present() 显式等待弹窗出现，再用 switch_to.alert.accept() 确认。

**困难3：邮箱重复导致测试失败**
测试创建的用户没被清理，下次跑测试邮箱冲突。后来设计了 created_ids 自动清理机制，每次跑完测试自动删除创建的数据。

## 二、技术基础（大概率问）

### Q11：Python 里列表和元组有什么区别？

| | 列表（list） | 元组（tuple） |
|------|------------|-------------|
| 写法 | `[1, 2, 3]` | `(1, 2, 3)` |
| 可变性 | 可以增删改 | 创建后不能改 |
| 场景 | 动态数据集合 | 固定配置、元素定位 |
| 性能 | 占用内存大一点 | 占用内存小，速度快一点 |

我项目里 Page Object 的元素定位全部用元组，比如 `BTN_ADD = (By.LINK_TEXT, '新增用户')`——因为定位方式创建后不需要改。

**追问：元组不能改，那 Page Object 里为什么用它？**
因为元素定位方式是固定的配置，不需要改。用元组一方面省内存，另一方面是不可变对象更安全——不会被意外修改。

---

### Q12：GET 和 POST 的区别？

| | GET | POST |
|------|-----|------|
| 用途 | 查询数据 | 新增/修改数据 |
| 参数位置 | URL 后面（明文） | 请求体里面 |
| 安全性 | 低（URL 会留在浏览器历史） | 相对高 |
| 幂等性 | 是（查多次结果一样） | 否（创建多次会多出数据） |
| 浏览器缓存 | 会被缓存 | 不会被缓存 |

**追问：PUT 和 POST 的区别？**
PUT 是幂等的——修改同一个用户多次，结果一样。POST 不是幂等的——创建多次，会产生多个用户。

### Q13：HTTP 状态码常见的有哪些？

| 状态码 | 含义 | 例子 |
|--------|------|------|
| 200 | 成功 | 查询成功 |
| 201 | 创建成功 | 新增用户成功 |
| 400 | 客户端错误 | 参数不对、缺少必填字段 |
| 404 | 未找到 | 查一个不存在的用户 |
| 500 | 服务器错误 | 数据库挂了、代码报错 |

**追问：200 和 201 的区别？**
200 表示"请求成功"（一般查询/修改/删除返回），201 表示"创建成功"（新增资源返回）。我项目里接口统一 HTTP 200 返回，在 JSON body 里用 `code` 字段区分业务状态。

### Q14：SQL 常见的增删改查语句？


### Q16：自动化测试和手工测试的区别？什么时候不做自动化？

| | 手工测试 | 自动化测试 |
|------|---------|-----------|
| 速度 | 慢 | 快（21 条用例 12 秒跑完） |
| 准确度 | 可能漏 | 每次一致 |
| 适用场景 | 探索性测试、一次性验证 | 回归测试、重复执行 |
| 成本 | 每次都要人力 | 一次投入，长期受益 |

**什么时候不做自动化：**
- 需求频繁变化（脚本要不断改）
- 一次性测试（投入大于收益）
- UI 频繁变动（维护成本太高）
- 需要人的主观判断（比如页面"好不好看"）
