## 坑 1：两个 MySQL 实例并存，数据对不上

### 现象
Apifox 调用 DELETE `/api/users/1` 返回 "用户不存在"，但 MySQL 客户端里能查到 ID=1。

### 原因
电脑上有两个 MySQL 服务：

| 服务名 | 端口 | 来源 | 用途 |
|--------|------|------|------|
| MySQL80 | 3307 | 自己装的 | Flask 连的 |
| mysqlzt | 3306 | 禅道自带的 | 从没用过 |

MySQL 客户端不指定 `-P` 时默认连 3306，进的是禅道的库。Flask 连的是 3307。**两边不是同一个 MySQL，数据自然不一样。**

### 解决
```powershell
# 管理员 PowerShell
sc.exe stop mysqlzt                    # 停掉禅道的 MySQL
sc.exe config mysqlzt start= disabled  # 禁止开机自启
```

只保留自己的 MySQL80 一个实例。

### 教训
- 排查 "数据库有但 API 说没有" → 第一步确认两边连的是不是同一个 MySQL 实例
- `SELECT @@port;` 确认当前连的端口
- `netstat -ano | grep "3306\|3307"` 看端口被哪些进程占了

## 坑 2：WSL 里 Flask 连不上 MySQL

### 现象
```bash
# WSL 里
python3 run.py
# → ConnectionRefusedError: Can't connect to MySQL server on '127.0.0.1'
```

### 原因
`app/config.py` 里：
```python
DB_HOST = os.getenv("DB_HOST", "127.0.0.1")
```

WSL 里的 `127.0.0.1` 指向 WSL 自己，不是 Windows。MySQL 在 Windows 上，当然连不上。

### 解决
在 WSL 的 `~/.bashrc` 里加：
```bash
export DB_HOST=192.168.32.1
```

`192.168.32.1` 是 WSL2 访问 Windows 的网关 IP（可通过 `ip route show default` 查看）。

之后 Flask 启动：
```bash
python3 run.py   # 自动用 DB_HOST=192.168.32.1
```

### 教训
- WSL2 和 Windows 网络是隔离的，各有各的 `127.0.0.1`
- WSL 访问 Windows 服务 → 用网关 IP（`ip route show default | awk '{print $3}'`）
- Windows 访问 WSL 服务 → 用 `localhost` 或 WSL 的 IP

## 坑 3：pytest 里的数据库校验也连不上

### 现象
Flask 接口能调通，但测试用例里的 `DatabaseChecker` 报错：
```
ConnectionRefusedError: Can't connect to MySQL server on '127.0.0.1'
```

### 原因
`tests/common/config.py` 也有一行：
```python
"host": os.getenv("DB_HOST", "127.0.0.1"),
```

测试框架有两层数据库访问：
1. Flask 的 API 请求 → 走 HTTP，用 `base_url`，走的是 `127.0.0.1:5000`（Flask 在 WSL 本机，能通）
2. `DatabaseChecker` 直连 MySQL → 走 TCP，用 `DB_HOST`，默认 `127.0.0.1`（WSL 本机没有 MySQL，炸了）

**第一条通了掩盖了第二条的问题。** 只有涉及 `db.get_user_by_id()` 这种"落地校验"的用例才炸。

### 解决
同上，`~/.bashrc` 加 `export DB_HOST=192.168.32.1`，两个文件都受益。

第一次跑测试：8 条通过，5 条失败（POST 返回 500 / `IntegrityError: Duplicate entry`）
第二次跑测试：失败更多

- 下次看到 IntegrityError 1062，第一反应：清理没生效，手动清

## 坑 5：测试日志放错了位置

### 最初的想法（错的）
把 `logging` 加到 `app.py`（后端代码）里。

### 为什么错
1. 你是测试，后端代码不归你管，真实工作里改不了
2. 后端代码有 bug 崩了，日志根本没执行到，啥也看不到

### 正确的做法
日志写在测试侧：

| 文件 | 写什么 | 为什么 |
|------|--------|--------|
| `pytest.ini` | `log_cli = true` 等配置 | 让 pytest 输出日志 |
| `conftest.py` | `created_ids` 的清理日志 | fixture 销毁是静默的，出问题只能靠日志 |
| `db_helper.py` | 连接成功/失败 | MySQL 连不上是最常见的问题 |
| `test_user_api.py` | **不写日志** | pytest -v 已经告诉你用例名和结果了 |

### 原则
**只在 pytest 自己说不清楚的地方写日志。** 用例通过/失败 pytest 说了，但后台自动清理、数据库连接状态——这些 pytest 不说，自己记。

## 坑 6：`resp.status_code` 和 `result["code"]` 分不清

### 现象
测试用例里有两个看起来很像的东西：
```python
resp = api_session.get(f"{base_url}/api/users/99999")
print(resp.status_code)    # → 200
print(resp.json()["code"]) # → 404
```

同一个请求，一个返回 200，一个返回 404，懵了。到底哪个是对的？

### 原因
这是 **两层状态码**，各管各的：

| | `resp.status_code` | `result["code"]` |
|---|---|---|
| **谁给的** | Flask 自动填 | 你在 `jsonify()` 里手写的 |
| **在哪** | HTTP 响应头（协议层） | JSON 响应体里（业务层） |
| **怎么拿** | `resp.status_code` | `resp.json()["code"]` |
| **标准** | HTTP 协议（RFC 标准） | 项目自己约定的 |
| **你项目里的值** | 几乎永远是 200 | 200 / 201 / 400 / 404 / 500 |

关键点：**Flask 的 `jsonify()` 默认返回 HTTP 200**。就算业务出错了，只要 `jsonify()` 执行成功，HTTP 层就是 200。真正的业务状态藏在 JSON 的 `code` 字段里。

```
客户端  ──── HTTP 请求 ────→  服务器
         ←── HTTP 响应 ────
              │
              ├── 响应头（Headers）
              │     └── status_code = 200    ← Flask 自动给的
              │
              └── 响应体（Body）
                    └── {"code": 404, ...}   ← 你手写的业务码
```

### 解决
测试里两个都要断言：
```python
resp = api_session.get(f"{base_url}/api/users/99999")

# 第1层：HTTP 通信本身成功了吗？（服务器正常返回了 JSON）
assert resp.status_code == 200

result = resp.json()
# 第2层：业务结果对吗？（用户确实不存在）
assert result["code"] == 404
assert result["message"] == "用户不存在"
```

### 如果想让 HTTP 状态码等于业务码？
```python
# 现在的写法 → HTTP 永远 200，业务码在 body 里
return jsonify({'code': 404, 'message': '用户不存在'})

# 更规范的做法 → HTTP 状态码也改掉
return jsonify({'code': 404, 'message': '用户不存在'}), 404
#                                                      ↑ 加这个
```

### 教训
- `resp.status_code` 是 HTTP 协议的，`result["code"]` 是业务逻辑的，两码事
- 你项目的设计是：HTTP 层永远 200，业务状态放 JSON body 里
- 面试被问"为什么用户不存在还返回 200" → 说明这是项目设计，不是 bug
- 大部分公司用第二种写法（HTTP 状态码 = 业务码），面试时说出这两种设计的区别就是加分项

### 💡 实战技巧：用两层状态码快速判断前后端问题

```
发请求 →
  resp.status_code 是什么？
        │
        ├── 500 / 502 / 503（HTTP 层就炸了）
        │     → 💣 后端问题
        │       服务器代码崩了、数据库挂了、Nginx 配错了
        │       连 JSON 都拿不到，业务逻辑根本没执行到
        │
        ├── 200（HTTP 层通了，服务器正常返回了 JSON）
        │     │
        │     └── result["code"] 是什么？
        │           │
        │           ├── 200 / 201 → ✅ 一切正常
        │           │
        │           ├── 400 → 🙋 前端问题
        │           │    参数不对：缺字段、格式错、空 body
        │           │    后端收到了请求，但校验不通过
        │           │
        │           ├── 401 / 403 → 🙋 前端问题
        │           │    没登录 / 没权限
        │           │
        │           ├── 404 → 🙋 前端问题
        │           │    URL 里的 ID 不存在，不是服务器坏了
        │           │    查/改/删了一个不存在的资源
        │           │
        │           └── 500 → 💣 后端问题
        │                JSON body 里返回 500
        │                数据库写入失败、唯一键冲突、代码异常
```

一句口诀：

| 现象 | 结论 |
|------|------|
| `resp.status_code` ≠ 200 | **后端炸了**，HTTP 层都没过去 |
| `resp.status_code` = 200，`result["code"]` 4xx | **前端问题**，请求参数/URL 不对 |
| `resp.status_code` = 200，`result["code"]` 500 | **后端问题**，业务逻辑/数据库出错 |

面试时面试官如果说"这个接口报错了"，你第一反应不是看代码，而是先看这两个 status——立刻能说出是前端还是后端的问题，这就是测试的专业素养。

## 坑 7：conftest.py 放哪层？不只是为了方便找

### 现象
项目有两个 conftest.py：
```
tests/
├── conftest.py          ← 公共 fixture（db, api_session, base_url, created_ids）
├── api/
│   └── test_user_api.py
└── ui/
    ├── conftest.py      ← driver fixture + --headless 参数
    └── test_user_ui.py
```

疑问：`driver` fixture 能不能直接放 `tests/conftest.py`？放 `tests/ui/conftest.py` 只是为了方便找到吗？

### 原因
pytest 的 conftest.py 是**层级生效**的：

```
子目录的测试能拿到所有祖先目录 conftest.py 的 fixture
当前目录的 conftest.py 只作用于当前目录及子目录
```

所以：
- `tests/ui/test_user_ui.py` 能拿到 `tests/conftest.py` + `tests/ui/conftest.py` 两个文件的 fixture
- `tests/api/test_user_api.py` 只能拿到 `tests/conftest.py` 的 fixture，拿不到 `tests/ui/` 下的

**技术上可以**把 driver 放 `tests/conftest.py`，但会导致：

1. **依赖污染（最关键）**：`tests/ui/conftest.py` import 了 `selenium`。放父级会让 API 测试运行时也 import selenium → 万一环境没装 selenium，API 测试也被连累炸掉
2. **作用域过大**：driver 只有 UI 测试用得到，API 测试不需要
3. **pytest_addoption 同理**：`--headless` 参数只需要在 UI 测试的 conftest 里注册

### 解决
保持现状，这就是正确的设计：

| 文件 | 职责 | 作用范围 |
|------|------|---------|
| `tests/conftest.py` | 公共基础设施（DB、HTTP 会话、数据清理） | tests/ 下全部 |
| `tests/ui/conftest.py` | 浏览器基础设施（WebDriver、headless） | 仅 tests/ui/ |

### 面试表达
> "公共 fixture 放父级 conftest.py，子目录各自放自己特有的 fixture。UI 的 WebDriver 放 tests/ui/conftest.py，遵循最小作用域原则，避免 API 测试被 Selenium 依赖污染。"

### 教训
- conftest.py 层级是 pytest 的核心机制，不能所有 fixture 都往顶层堆
- 判断 fixture 放哪层的标准：**哪些测试需要它，就放在刚好能覆盖那些测试的那一层**
- 依赖隔离 > 统一管理

## 坑 8：alert 弹窗间歇性报 NoAlertPresentException（第3周）

### 现象
```python
driver.find_element(...).click()     # 点删除按钮
alert = driver.switch_to.alert       # → NoAlertPresentException（间歇性）
```

有时候过，有时候不过，非常不稳定。

### 原因
alert 弹窗不是瞬间出现的。JavaScript `confirm()` 从执行到浏览器渲染弹窗有 50-200ms 延迟。代码跑得比浏览器快——代码已经执行到 `switch_to.alert` 了，但弹窗还没渲染出来。

### 解决
```python
# ❌ 错误：直接拿 alert（弹窗可能还没出来）
alert = driver.switch_to.alert

# ❌ 也不好：盲等 1 秒（浪费时间，且不可靠）
time.sleep(1)

# ✅ 正确：用显式等待，弹窗出现立刻拿到
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

alert = WebDriverWait(driver, 5).until(EC.alert_is_present())
```

### 原理
`EC.alert_is_present()` 内部循环检查 alert 是否出现，出现了立即返回，没出现每 0.5s 重试一次，最多等 5 秒。

### 教训
UI 测试里任何"不是瞬间完成"的操作都要加显式等待。`time.sleep` 是万不得已才用的。

## 坑 9：编辑页数据预填验证失败（value 为空）（第3周）

### 现象
```python
edit_page.open(base_url, user_id)        # 打开编辑页
value = edit_page.get_name_value()       # → ""（预期是"张三"）
```

### 原因
编辑页 `edit.html` 的数据不是后端渲染的——是页面加载后发 AJAX GET 请求拿数据，再用 JavaScript 填到输入框。所以流程是：

```
页面加载 → 输入框还是空的 → AJAX 请求发出 → 服务器返回数据 → JS 填到输入框
          ↑ get_name_value() 这时候执行 → 拿到空值！
```

### 解决
```python
# 等输入框的 value 属性不为空（说明 AJAX 已完成）
from selenium.webdriver.common.by import By

WebDriverWait(driver, 5).until(
    lambda d: d.find_element(By.ID, 'name').get_attribute('value') != ''
)
```

### 教训
- 判断数据是怎么来的——后端渲染（同步）还是 AJAX 加载（异步）
- 异步加载的数据需要显式等待，不能用隐式等待（隐式等待只等"元素存在"）

## 坑 10：HTML5 required 属性和 JS 校验冲突（第3周）

### 现象
缺姓名提交 → 期望看到 JS 的自定义错误提示（红色文字）→ 实际看到的是浏览器默认气泡提示

JS 校验代码根本没执行到。

### 原因
```html
<form onsubmit="return validateForm()">   ← JS 校验
    <input required>                       ← HTML5 校验（浏览器内置）
    ...
</form>
```

HTML5 校验优先执行——如果 `required` 字段为空，浏览器直接弹气泡，表单根本不会触发 `onsubmit`，JS 校验函数永远不会被调用。

### 解决
```html
<form onsubmit="return validateForm()" novalidate>
    <!--                       ↑ 加了 novalidate -->
```

`novalidate` 告诉浏览器"跳过 HTML5 校验"，让 JS 全权负责校验逻辑。

### 教训
HTML5 校验是浏览器原生行为，JS 校验是自定义行为，两者不是"互补"而是"互斥"——HTML5 先拦截。

## 坑 11：Chrome 驱动版本不匹配 → 换 Edge（第3周）

### 现象
```
selenium.common.exceptions.SessionNotCreatedException:
This version of ChromeDriver only supports Chrome version 132
Current browser version is 134
```

### 原因
Chrome 浏览器自动更新，但 pip 装的 chromedriver 版本没跟上。

### 解决
换用 Microsoft Edge：
```python
# ❌ Chrome：需要手动管理 chromedriver 版本
driver = webdriver.Chrome()

# ✅ Edge：Windows 自带，Selenium 4.x 自动适配驱动
driver = webdriver.Edge()
```

Edge 和 Chrome 是同一个内核（Chromium），Selenium 操作完全一样。但 Edge 驱动由 Windows 自动维护，没有版本匹配问题。

### 教训
Windows 上做自动化优先用 Edge——不需要额外装浏览器，也不会有驱动版本问题。

## 坑 12：YAML 布尔值导致 .lower() 报错（第4周）

### 现象
```python
# config.yaml 里: debug: true
DEBUG = _get("app.debug", "FLASK_DEBUG", True).lower() == "true"
# → AttributeError: 'bool' object has no attribute 'lower'
```

### 原因
YAML 里 `true`（不加引号）被 `yaml.safe_load()` 直接解析成 Python 布尔值 `True`。代码期望拿到字符串 `"true"` 然后 `.lower()`，但拿到的是布尔值。

### 解决
```python
# ✅ str() 统一转字符串再比较
DEBUG = str(_get("app.debug", "FLASK_DEBUG", True)).lower() == "true"
# str(True) = "True" → "true" → "true" == "true" ✅
# str("true") = "true" → "true" → "true" == "true" ✅
```

### 教训
YAML 有类型推断：`true`/`false` → 布尔，`123` → 整数，`1.5` → 浮点。读配置时要注意类型不一致的问题。

## 坑 13：Windows GBK 编码不支持 emoji（第4周）

### 现象
```python
print(f"📁 配置文件: {path}")  # → UnicodeEncodeError
```

### 原因
Windows 终端默认 GBK 编码（兼容中文但只支持 2 字节字符），emoji 是 4 字节 UTF-8 字符，GBK 没法编码。

### 解决
代码注释和日志里不用 emoji，用纯文字即可。

## 坑 14：.gitignore 行尾注释导致规则失效（第4周）

### 现象
`reports/` 目录没被忽略，但 `.gitignore` 里明明写了 `reports/`

### 检查
```bash
git check-ignore -v reports/    # 没输出 → 说明没被忽略！
```

### 原因
```gitignore
reports/           # pytest-html 生成的报告
# ↑ 行尾注释可能有不可见字符干扰匹配
```

### 解决
```gitignore
reports/
# ↑ 去掉行尾注释，干净的一行
```

### 验证
```bash
git check-ignore -v reports/    # .gitignore:19:reports/	reports/ → 生效了！
```

### 教训
`.gitignore` 里每行规则尽量简洁，行尾注释有时会导致匹配失败。出问题用 `git check-ignore -v` 排查。

## 坑 15：Git 首次提交缺少用户配置（第4周）

### 现象
```
git commit -m "消息"
→ Author identity unknown
→ Please tell me who you are.
```

### 原因
Git 每次提交都会记录作者信息（name + email），首次使用需要先配置。

### 解决
```bash
git config --global user.name "你的名字"
git config --global user.email "你的GitHub注册邮箱"
```

⚠️ **邮箱一定要用 GitHub 注册邮箱**，否则 GitHub 上不显示贡献绿点和头像。
